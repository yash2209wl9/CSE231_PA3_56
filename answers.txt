C-Q4. Why is pthread_cond_broadcast(&q->not_empty) appropriate during shutdown? What could go wrong with waking only one waiting consumer?
Answer:
When shutdown happens, all 4 printer threads might be sleeping on not_empty waiting for jobs. Now, if we use signal than it only wakes up 1 consumer thread(while others are still sleeping). That one thread wakes up, sees count is 0 and shutdown is 1, and exits. But now, other 3 printer threads are still sleeping and no new jobs will be inserted in queue by producers, so no wake-up signal is going to be there. So, the upcoming thread will chain after the front one and this chain can't be moved, so other threads will stay sleeping in cond_wait till eternity. So, deadlock condition is there when main tries to join and nothing can open them. So, to stop this random flow of code, we need broadcast to wake all 4 printer threads together so all threads see shutdown is 1 and exit instead of hanging forever.


C-Q5. Why is a condition variable preferable to busy waiting when the queue is empty for a long time?
Answer:
If thread repeatedly locks, checks count, and unlocks in a loop than it is just busy-waiting/spinning and burns its whole CPU time slice for doing nothing. Now, another thread(like producer) also wants to insert in queue, but mutex is locked again and again by the spinning thread, so metadata is blocked and producer will drift away and get delayed in inconsistent intermidiate state. Now(in general), condition variable is much better because pthread_cond_wait sends them to sleep in blocked state so it consumes zero CPU, and only wakes up when producer actually inserts in queue and sends wake-up signal.
